# FR-RECEIPT-01 简化企业线下收款规格草案

状态：APPROVED，用户已逐项采纳“先账正确→登记界面→同单演示”，确认本地验收与三个步骤。此前代码不因此自动验收通过。当前状态只维护在 OPERATIONS-USABILITY-PLAN.md 顶部。

## 用户已确定的需求

企业沿用普通商品、规格、购物车、配送及提交订单流程，采用线下付款。订单提交为待收款，不因送达而已付款。有权限运营登记实际金额、时间、方式、备注，显示未收款/部分收款/已收齐；记录操作者，重复提交不重复累计。企业定价是否等同个人尚未决定，保持现有规则。不删除企业资料和历史订单。

## 已确认的验收接缝

主要验收通过实际 API dispatch 与后台订单界面，而非仅调用金额计算函数。存储和文件服务替换为本地隔离适配器，所有测试明确标为本地。用同一订单串联实际 orders.create → 待收款 → 后台登记第一笔 → 部分收款 → 第二笔 → 已收齐 → 重试不重复。附权限、失败、并发、履约独立的负面用例。

这不等同于真实小程序操作、微信身份登录、银行实际到账或 CloudBase 事务验证。禁止为演示写线上数据。

## 接口契约草案 v1

- `admin.orders.receipts.list`：receipts.read；输入 orderId；返回订单号、总额、累计实收、待收、收款状态及流水。界面通过订单打开，不让人填写内部 ID。
- `admin.orders.receipts.record`：receipts.write；输入 orderId、整数分 amountCent、带时区 receivedAt、method、note、idempotencyKey。界面按元输入、北京时间可读显示，转换由后台代码处理。
- 同凭据同内容重试返回原流水，改变内容报错；累计不得超过订单金额。金额更新、流水和审计必须同事务成功或全部回滚。
- 收款方式是人工登记标签，不调用微信支付或银行扣款；界面须提示先核实真实到账。备注不作为到账证明。
- 收款只更新收款字段，不更改履约状态、价格快照和订单总额；已收款订单禁止直接取消。线下退款、错账冲正暂不新增自动处理，明确提示人工核实，不能静默抹掉流水。
- 新订单 offline_pending + unpaid；部分收款 offline_partial + partial；收齐 offline_paid + paid。与在线 paid 区分，避免误走在线退款。
- 历史 not_required 只说明无需在线支付，不证明未收或已收；缺少可信实收记录应标“历史收款待核实”。缺字段默认零及旧状态误判已修正并回归验证，不将它直接当成历史事实。
- 零/负/超额金额、未来或非法时间、无权限、非线下订单、已取消/退款异常、同凭据不同内容必须明确拒绝，且不得部分写入。
